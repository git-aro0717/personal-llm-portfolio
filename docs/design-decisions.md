# 技術選定と設計判断

コード・既存設計書・開発指示から確認できる判断を整理した。性能比較実験で優位性を実証した資料ではない。

| 選定・判断 | 目的 | トレードオフ・代替案 |
|---|---|---|
| Backend / Harness / adapter分離 | HTTPとプロバイダー形式の変更を局所化 | 一つの関数へまとめるより経路が増える。全機能がプロバイダー共通になるわけではない |
| FastAPI / Pydantic | APIと型・制約のある入力検証 | モデル出力や業務上の正しさは別途検証が必要 |
| Mock維持 | 認証・課金に依存しない回帰と異常系確認 | 実サービスの反映遅延・利用権限は再現し切れない |
| Lambda / Mangum / SAM | 既存FastAPIを保ちクラウド実行・構成管理 | コールドスタート、IAM、イメージ配備の複雑さ。常駐サーバーとの実測比較は未実施 |
| Python 3.13 ARM64 | 開発PCとLambdaイメージのアーキテクチャ整合 | 他環境でのDocker/SAM互換性を別途確認する必要がある |
| localhost中継 + SigV4 | ブラウザにAWSキーを渡さずAWS_IAMを維持 | PC起動・認証設定が必要。公開Webアプリの認証を提供しない |
| Secrets Manager / AWSCURRENT | Lambda環境変数へAPIキー平文を置かない | 取得権限とOpenAIキーの有効性は別。取得通信と費用が発生する |
| OpenAI File Search | 独自検索基盤を増やさず文書検索 | 外部保管・料金・サービス依存。Bedrockへの検索移植は別設計 |
| SQLite / 先行記録 | 外部DELETE前に拒否状態を確定し再起動後も維持 | ローカル専用。Lambdaや複数プロセスを含む分散削除保証はない |
| CSVをTXTへ変換（v1.1） | 行・列・値を残して既存文書経路を使う | 厳密集計やDB検索の代替ではない。数式評価・書戻しを行わない |
| textContent表示 | 文書名・モデル回答をHTMLとして実行しない | Markdown整形をそのまま表示できない |

## LLMとシステムの切り分け

- モデルに依存：回答品質、推論、言語表現、検索ツールの利用判断。
- システムに依存：認証、入力上限、対象ID許可、削除開始の拒否、再試行方針、エラーの安全化。
- サービスに依存：索引化状態、削除反映タイミング、モデル利用権限、API料金。

自然言語で「削除して」と伝えることを削除権限と扱わず、検証済みAPIと承認された対象に限定した。
APIのDELETE 200だけで消失完了を宣言せず、個別GETの確認とローカル拒否を分けて扱った。

## 障害から得た判断

| 問題 | 確認・対応 | 現在の範囲 |
|---|---|---|
| `secret_unavailable` | 取得失敗とJSONの`api_key`形式・空値を切り分け | JSON形式で取得。秘密値をログに出さない |
| OpenAI認証失敗 | Secrets参照権限とキー自体の有効性を区別。手動更新後のModels GETと実推論を段階検証 | v1.0実E2E成功は過去の記録。今回再通信していない |
| DELETE直後のGET 200 | 期限・回数を限定した確認、元Filesと関連付けの独立観測、台帳・cleanup | 遅延や未確認を削除要求失敗と断定しない |
| OneDrive内の台帳置換エラー | 検証台帳をOneDrive外TEMPへ。削除状態DBもGit・OneDrive外に限定 | 稼働DBや私的台帳を公開しない |
| 古いローカルプロセス | 起動設定・DB保存先を調査し対象を限定して移行 | UI・ソース更新だけでは稼働プロセスが更新されない |

SAM/Dockerの接続・ビルド障害は開発記録に残るが、あらゆる環境に共通する単一原因が証明されたとは扱わない。
API本文取得の追加診断HTTP 400は原因未確定。通常検索の成功とは分けている。
